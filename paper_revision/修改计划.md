## 8. D2 Agent 工具 baseline 实验协议（草案）

**目的**：回答学长建议 #3 —— 用现成 AI Agent/CLI 工具执行相同任务，对比与 DentalClaw 的决策质量。

**基线对象（选 2–3 个，按可用账号）**：
- Claude Code（Anthropic 的 agentic CLI）
- OpenAI Codex CLI
- 国产 Agent 工具 1 个（Qwen Code / GLM coding agent / DeepSeek 系，视可用性）

**任务集**：与平台同一批意图（30 条全集，D1 已定），中英文原样输入。

**统一输入（公平性关键）**：每个 baseline 只拿三样东西——
1. 意图原文；
2. 结构化环境描述：可用数据集（TDD/ToothFairy3/私有）、已验证方法注册表清单（task_family/modality/mode 路由表）、代码资产描述；
3. 同一输出约束：返回 JSON 决策 `{outcome: use_registry|external_proposal|reject, selected_method, rationale, requires_human_review}`。

**只测决策、不跑执行**：baseline 与 DentalClaw 推理层同等安全地位（决策不允许真实执行训练/推理），避免 GPU 开销与不可比因素。

**为什么只测决策层是合理且必要的（设计理由，写论文用）**：
1. 论文核心主张是决策层（intent→路由→fail-safe），30 条意图评测测的就是决策正确性；baseline 用同一把尺子才公平。
2. 通用工具没有平台的注册表/skill 层/执行模块，让它们端到端执行 = 让它们从零重建平台，测的不是同一个东西，也不可比。
3. 成本与安全：3 工具 × 30 条的 GPU 训练不可行；也不应让外部工具在真实数据上随意执行。
4. 结论价值：对比直接暴露“通用助手倾向于猜（ambiguous 0.739 vs 平台 1.0），平台倾向于保守澄清”——这正是平台设计的价值证据，符合学长“比我们好就放”原则。
5. limitations 如实写：只测决策行为而非端到端执行；baseline 拿到的是环境描述而非可操作运行环境（区别于 WildClawBench 的真实 runtime）；单次运行；系统提示不受控。

**打分**：用同一套预定义期望行为 + 同一六维 rubric（权重不变）打分，输出每 baseline 的均值 + 四类意图分组得分，与 DentalClaw 对比。

**报告位置**：Results 3.2 后加一小节（或 Supplementary 表 + 正文一段）；学长要求“比我们好才放”作为默认原则，若持平/更好则如实报告并讨论。

**必须写的 limitations**：baseline 无 DentalClaw 的 skill 层与确定性注册表（这本身就是本平台的贡献点）；对比限于决策行为而非端到端执行；温度/系统提示用各工具默认配置。

**工作量估算**：25 意图 × 3 工具 × ~1–2 min/条，仅 API 费用，无 GPU，1 天内可完成。

## 10. “Appropriate evaluation”（R4 #3）解决策略

> 背景：R4 质疑的不是有没有 QC，而是系统是否会选择**方法学上合适**的方案（为什么是分割不是检测/分类、评估单位、指标、偏倚、外部验证、ground truth 适配）。D4 已定不做独立专家实验，用“机制+证据+诚实承认”四层回应。

**第 1 层 机制写清楚（改正文 2.4/2.5）**：适当性不是 LLM 运行时决定的，而是先验编码在规格链里（已在代码中核实）：
- `platform_mvp/method_registry.json` 的 `scope_policy`（allowed_domain / allowed_modes / reject_or_explain）
- 方法条目：task_family ↔ task_variant ↔ modality ↔ allowed_modes ↔ framework ↔ workflow ↔ expected_outputs
- `artifacts/results/specs/task_spec_*.json`：task_type + `primary_metric`（如 mean_dice）
- `artifacts/results/specs/dataset_spec_*.json`：标注布局（labelsTr/labelsVal）+ label_format + image_domain
- 表述：把注册表从“金标准”改为“研究组先验编写的、任务对应的适当性规格”；用 “prespecified, task-appropriate evaluation specifications”，不写 “appropriate evaluation” 大词。

**第 2 层 注册表补字段（T6，半天代码活）**：每条方法显式声明 `required_annotation_type`（mask/bbox/case-label）、`evaluation_unit`（image/tooth/lesion/case）、`evaluation_metrics`、`required_qc_gates`、`contraindications` → 适当性规格变成审稿人可直接检查的显式声明。

**第 3 层 行为证据（已有数据）**：trap/boundary 意图即“不选择不适当方法”的证据（ResNet 做分割→外部提案不执行；分类→澄清；非牙科→拒绝）。Results 3.2 加一句：“没有任何被评估请求执行了任务规格不匹配的方法”。

**第 4 层 诚实承认（D4）**：limitations 写“规格链由研究组按领域惯例编写、未经独立专家按正式 rubric 验证”；future work = 独立专家 rubric。response R4 #3 按此四层重写。

**与六维框架的关系（重要口径，勿混）**：
- 六维框架（planning/qc_blocking/... 0.958）测的是**决策保真度**：平台实际行为与预设期望的一致程度（已核实 `eval_platform_mvp.py` 六个 `score_*` 函数全部是 actual vs expected 比较）。若预设本身方法学有错，评分仍会给高分——所以它不能回答 R4 #3 的“预设是否适当”。
- 六维框架的**价值定位**：它是“不选择不适当方法”的**行为证据生产工具**（qc_blocking 对应数据层偏倚；trap 意图把方法学不当组合编码为必须拒绝）。
- R4 #3 与六维的对应：完整性/标注/泄漏 → qc_blocking + QC 段（已覆盖）；评估单位/标注类型/禁忌组合 → T6 注册表字段（待补）；指标选择 → task_spec `primary_metric`（已有，需显式声明）；外部验证/设计层偏倚 → limitations（D4 承认）。
- ⚠️ **不动六维结构与权重**：30 条评测（0.958）已完成并写入 v3，改动需重跑全部评测；适当性断言进注册表字段（T6），框架保持原样。

**备选升级（若学长/审稿人仍不满意）**：研究组内部 rubric 审计——书面 rubric 应用到全部 N 条计划、报告一致率、明确标注非独立（1–2 天，比纯 limitations 强，比独立专家轻）。
